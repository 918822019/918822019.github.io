# 为什么INT8量化了推理增加了计算量但是计算更快

## INT8量化
INT8量化，是深度学习模型量化的一种方式，将模型中的权重和激活值进行量化，从而减少模型大小，提高模型推理速度。  
核心计算公式可以表示为  
Q = round(R / S + Z)  # 量化：浮点数R → 整数Q  
R = (Q - Z) * S  # 反量化：整数Q → 浮点数R  
当我们做INT8推理的时候，模型需要先经过反量化得到浮点数，再进行计算，这一步引入了额外的计算量。  
举个例子，比如我们计算一个1024 4096的线性层，输入为1 * 1024在fp16精度下，我们应该是  
1 * 1024 * 4096 * 2   
而如果我们做了量化，那么在计算过程中我们需要做反量化  
计算量变成了 1024 *4096 * x(量化系数)这个量化系数可以看作常数，所以最后变成了 1024 * 4096 + 2 * 1024 * 4096
这么看起来好像反量化占据计算量很大，但是我们在实际计算中一般是通过并发批量计算。所以输出其实一般会变成  
32 * 1024  
计算会变成1024 * 4096 / 1024 * 4096 +32 * 2 * 1024 *4096  
1 / 1 + 2 * 32 约等于 1.5%  
这么一看是不是反量化的计算量下来了。
除此以外，INT8因为整数的问题，导致其计算的速率远高于的fp16,我们这里是假设INT8和fp16的计算速度是一样的，所以其实在真实计算中，INT8
的计算时间是可以进一步压缩的。  
其次，大模型分为prefill阶段和decode阶段，前者是计算密集型，依赖显卡的计算核心。decode阶段反而是i/o密集型，需要不停的从显存单位搬运到
计算核心中，极度依赖内存带宽，而INT8相当于减少了一半的数据传输量，提高了decode阶段一半左右的解码速度，而解码速度反而是大模型推理的时间
重头部分，因此才有INT8比fp16的计算速率更快，尽管在数学表现上确实增大了计算量


## ⚠️ 重要说明：为什么在 CPU/NumPy 上看不到加速？

### 问题现象
如果你在 CPU 上使用 NumPy 测试 INT8 量化，可能会发现：
- ❌ INT8 推理速度和 FP32 差不多
- ❌ 甚至可能更慢
- ❌ 看不到预期的 2-4 倍加速

**这是正常的！原因如下：**

### 原因 1：NumPy 没有 INT8 硬件加速

```python
# NumPy 的 INT8 矩阵乘法实际上是这样执行的：
def int8_matmul_numpy(a_int8, b_int8):
    # 步骤 1：转换为 INT32（有开销）
    a_int32 = a_int8.astype(np.int32)
    b_int32 = b_int8.astype(np.int32)
    
    # 步骤 2：调用 BLAS 库（OpenBLAS/MKL）
    # 这些库主要针对 FP32/FP64 优化，对 INT32 没有特殊优化
    result = np.dot(a_int32, b_int32)
    
    return result
```

**问题：**
- OpenBLAS/MKL 主要优化了 FP32/FP64 的 SIMD 指令（AVX2/AVX-512）
- INT32 没有专门的向量化优化
- 类型转换（int8→int32）引入了额外开销

### 原因 2：CPU 缺乏专用的 INT8 计算单元

```
GPU (A100/H100) 架构：
┌──────────────────────────────────────┐
│  Tensor Core（专用硬件）              │
│  • FP16 × FP16 → FP16               │
│  • INT8 × INT8 → INT32  ← 专门优化！ │
│  • INT4 × INT4 → INT32              │
│  吞吐量：INT8 是 FP16 的 2-4 倍      │
└──────────────────────────────────────┘

CPU (x86) 架构：
┌──────────────────────────────────────┐
│  AVX-512 VNNI（有限支持）             │
│  • 需要手动使用 intrinsics            │
│  • NumPy 默认不使用                   │
│  • 需要专门的库（如 Intel MKL-DNN）   │
└──────────────────────────────────────┘
```

### 原因 3：量化/反量化的固定开销

```python
# INT8 推理的完整流程
input_fp32 → quantize → input_int8      # 开销 1：找 max + 除法 + 取整
input_int8 × weight_int8 → output_int32  # 应该快的部分
dequantize → output_fp32                 # 开销 2：乘法

# 在小矩阵上，开销 1+2 占比很大
# 只有在大矩阵 + GPU 上，矩阵乘法的加速才能 amortize 这些开销
```

## ✅ 如何看到真正的 INT8 加速？

### 方法 1：使用 GPU + TensorRT

```python
import tensorrt as trt

# TensorRT 会：
# 1. 调用 cuBLASLt 的 INT8 GEMM kernel
# 2. 使用 Tensor Core 硬件加速
# 3. 自动优化内存布局和 layer fusion

# 预期加速：
# A100: INT8 比 FP16 快 2-3 倍
# H100: INT8 比 FP16 快 3-4 倍
```

### 方法 2：使用优化的 CPU 库

```python
# Intel MKL-DNN (oneDNN)
# 支持 AVX-512 VNNI 指令集的 INT8 优化

import torch
# PyTorch + oneDNN 可以在 CPU 上看到一定加速
# 预期：INT8 比 FP32 快 1.5-2 倍（取决于 CPU 型号）
```

### 方法 3：增大矩阵尺寸

```python
# 小矩阵：量化开销占比大
matrix_size = 128 × 128  # INT8 可能更慢

# 大矩阵：矩阵乘法主导，加速明显
matrix_size = 4096 × 4096  # INT8 更快
```

### 方法 4：使用批量推理

```python
# 小 batch：量化开销占比大
batch_size = 1  # 每次都要重新计算 input scale

# 大 batch：摊销固定开销
batch_size = 32  # 更高效
```

## 🎯 总结

1. **INT8 加速需要专门的硬件和软件支持**
   - GPU: Tensor Core + TensorRT/cuBLASLt
   - CPU: AVX-512 VNNI + oneDNN/MKL-DNN

2. **NumPy 不是测试 INT8 性能的正确工具**
   - NumPy 主要针对 FP32/FP64 优化
   - INT8 在 NumPy 上可能更慢

3. **生产环境应该使用**
   - GPU: TensorRT, ONNX Runtime (CUDA EP)
   - CPU: OpenVINO, oneDNN, llama.cpp

4. **加速的主要来源**
   - 硬件：Tensor Core 的 INT8 专用电路
   - 带宽：INT8 数据传输量减半
   - 缓存：更多权重可放入高速缓存
