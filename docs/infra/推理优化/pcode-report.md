# Pcode 技术报告（精简版）

> 证据截至 2026-10-10；整理发布于 2026-10-22。本文依据已汇总的源码核对结论与实验记录整理，未核查证据截止日期之后的新增进展。

## 摘要

Pcode 用两个并行的小分类头替代 drafter 的全词表输出头，在保留一次块主干前向的同时，显著压缩输出参数与读出成本。E3 进一步压缩输入侧，形成约 **29.7 MB 的 draft 侧交付包**。

这种压缩伴随接受长度下降。在现有统一 GPU 对照中，Pcode E3 的相对 AR 速度为 **2.70×**，低于 full-head 的 3.16× 和固定子词表的 3.03×。手机端约 1.70× 的加速，仅在已通过逐 token 一致性检查的特定 CPU 路径及小样本内成立。

因此，Pcode 当前最明确的价值是**紧凑读出与交付成本**。速度、输出一致性和峰值内存仍须分别验收。

## 1. 问题与设计选择

投机解码先由轻量 drafter 提出一段草稿，再由 target 验证。对于单 token 推理本身较便宜的小 target，drafter 必须足够轻，额外的草稿计算才可能换来整体收益。

传统 drafter 的全词表输出矩阵较大，读出成本高。串行字节头虽然参数较少，却引入循环和前后依赖。Pcode 的设计是：**保留一次块主干前向，将每个位置的 token 预测拆成两个独立的小分类，再通过固定表还原 token ID。**

当前实验线使用 Qwen2.5-0.5B-Instruct 作为 target；drafter 为三层 DFlash / DFlare，hidden size 为 896，读取 9 路 target 特征。block8 通常包含一个 anchor 和七个草稿位置。

## 2. 双码读出的实现

对每个草稿位置的隐藏状态 H，两个分类头独立预测码位：

```text
a = argmax(Head_A(H))          # 896 → 390
b = argmax(Head_B(H))          # 896 → 390，不依赖 a
token_id = repair[a × 390 + b]
```

两个码位共同索引固定解码表。这里的“并行”指两个头之间不存在串行条件依赖。

| 项目 | 实现与含义 |
| --- | --- |
| 编码容量 | 390 × 390 = 152,100，可覆盖 151,936 个 token，剩余 164 个空槽。 |
| bytewise 编码 | 将 token 按字节路径的字典序排列后填表；两个码位并不是两个 UTF-8 字节。 |
| random 对照 | 使用相同编码容量的随机编码，作为编码方式的对照。 |
| repair 表 | 将码位组合映射为合法 token，空槽也映射到合法 token；合法不代表预测正确。 |
| 输出参数 | 双头共 699,660 个参数，约 0.70M；全词表输出矩阵约有 136M 个权重。 |

输出权重规模约缩小 **195 倍**。这一比较只针对输出头，不能直接解释为整个系统的内存、模型文件或生成耗时也缩小相同比例。

## 3. 训练、验证与无损边界

训练时，监督 token y 经固定编码表转换为目标码位 (a*, b*)，两个头分别计算交叉熵：

```text
(a*, b*) = encode(y)

L = CE_A + CE_B
  = −log q_A(a*; H) − log q_B(b*; H)
  = −log [q_A(a*; H) × q_B(b*; H)]
```

即**概率相乘，负对数损失相加**。损失经 D-PACE 训练流程参与主干更新。E2 从头联合训练，让主干状态适应双码读出。

推理时，Pcode 只负责提出草稿 token。target 验证连续前缀、纠错，并回滚未接受部分的 KV 缓存。草稿预测质量主要影响接受长度与速度。

实际实现是否保持输出一致，还需与**同计算路径的自回归基线（AR）逐 token 对拍**。量化方式和计算形状的变化可能造成 argmax 分歧，仅有 target 验证机制不足以替代实际验收。

## 4. E2 与 E3：从输出压缩到双侧压缩

| 版本 | 输入侧 | 输出侧 | 主要价值 |
| --- | --- | --- | --- |
| E2 | 大词表 token embedding | Pcode 双码头 | 压缩输出，消除串行字节读出。 |
| E3 | 小型字节路径编码器 | Pcode 双码头 | 同时去掉输入、输出的大词表矩阵依赖。 |

E3 端侧使用 **CSR 路径表与惰性／异步组合**，替代约 260 MiB 的烘焙输入表，并完成 INT4 格点打包。实验记录中的 draft 侧交付约为 **29.7 MB**，不包含 target，也不是进程驻留内存（RSS）。

交付运行时已采用外部 driver，链接未修改的上游 MNN。在 x86 验收中，外部 driver 与 patched 引擎的 128 条输出逐 token 一致。这一结果验证了该运行时迁移路径，跨设备一致性仍需单独检查。

## 5. 实验结果与解释

### 5.1 统一 GPU 对照

实验使用 GSM8K test 前 256 题、user-only 输入、greedy 解码、max-new 2048、batch = 1，以及相同的 target HQQ/bf16 配置。相对速度采用各方法同一次运行中的 AR 对照。MAL 为实验记录中的平均接受长度，沿用原记录统计口径。

| 方法 | MAL | 相对 AR 速度 |
| --- | --- | --- |
| DFlash full-head | 4.09 | 3.16× |
| 固定子词表 | 3.90–3.92 | 3.03× |
| **Pcode E3** | **3.53** | **2.70×** |

在这组统一对照中，Pcode E3 实现了相对 AR 的加速，但接受长度和最终生成速度均低于另外两种方案。现有证据支持其压缩价值，尚不支持速度领先的结论。

### 5.2 历史 E2 对照：读出成本与接受长度的交换

| 指标 | 串行 byteio | Pcode E2 |
| --- | --- | --- |
| MAL | 3.91 | 3.74 |
| 头部微基准耗时 | 1.38 ms／轮 | 0.23 ms／轮 |
| 相对 AR 生成速度 | 2.85× | 2.85× |

双码头的读出耗时下降，补偿了一部分接受长度损失，最终生成速度持平。头部微基准约六倍的差异，不能解释为完整生成也加速六倍。历史 E2 与统一 GPU 对照的实验口径不同，数值应在各自对照内解释。

### 5.3 手机端：按计算路径分别验收

| 路径与样本 | 观测结果 | 结论边界 |
| --- | --- | --- |
| PEQM00 CPU high/normal，4 题 × 2 次 | b4 请求吞吐 7.41 tok/s，AR 为 4.36 tok/s，约 1.70×；8/8 输出一致。峰值 RSS 约 3,972 MiB，AR 约 2,874 MiB。 | 小样本加速通过一致性检查，但峰值内存明显增加。 |
| PEQM00 CPU low/low 复测 | 两轮逐 token 对拍的一致率均为 0/8。 | 未通过无损验收；吞吐结果只能用于诊断。 |
| PEQM00 OpenCL 归因 | target 多 token 计算成本高；已测试的现成替代 GEMM 路径更慢。 | 尚未完成 GPU 提速修复。 |

手机端证据表明，交付包体积小并不必然带来低运行内存；某条 CPU 路径上的成功，也不能直接推广到其他功耗配置或 OpenCL 路径。

## 6. 当前判断与下一步

**已证明：**一次块前向与独立双码读出可用；E3 的紧凑输入、输出及 MNN 交付链路已经落地；特定手机路径上存在经输出一致性检查的小样本加速。

**尚未证明：**全面优于 full-head 或固定子词表、跨设备稳定加速、所有量化路径无损，以及小模型包必然带来低运行内存。

后续工作按以下顺序推进：

1. 在目标设备的实际交付路径上完成逐 token 一致性验收，尤其排查 low/low 路径的分歧。
2. 采用配对的整请求测量，联合报告吞吐、输出一致性和峰值 RSS，并扩大样本。
3. 在通过验收的路径上扫描码容量与块尺寸，优化“实际提交 token 数／整轮成本”。

接受长度增加本身不构成加速，头部微基准也不能替代完整生成测量。Pcode 的进一步优化，应以实际交付路径上的端到端收益为依据。
