# 起点AI搜书

## 背景

通过AI结合用户提问，返回符合用户query的书籍。用户可以直接点进去，并且同时返回推荐这本书的理由。


## 模型
模型他们使用的是Deepseek-r1,为什么没有使用hunyuan不知道，猜测是因为模型能力比较差。 

在query进入模型之前，会进行预处理，有一次过滤，将一些不相关的query过滤掉，但是模型效果比较差。

example：
```python
query:你好
这个query是可以被过滤掉的
query:你是什么模型
这个query就给我路由到搜索模型，模拟器，建模相关的小说去了
```
## 数据召回
这里看不到数据是怎么召回的，是走的RAG还是参考的claude code通过agent的去自行search总结拿到数据。

但是他的响应速度比较快，这里猜测应该是通过RAG召回的，不然通过agent自行search，summary的结果会很慢。

这里我是根据他的思考过程去反推他的rag召回，首先rag召回肯定是做过embedding的，并且embedding，会对小说做好的summary，同时会考虑使用书籍的标签进行多路召回。有没有通过提取关键词，然后进行精确搜索作为一路召回目前存疑

这里可以自行测试一下，输入query，会先等待3-5s左右的时间。

猜测应该是query改写 + RAG。

然后llm会吞吐他的思考过程，这时候会出现很多的作品，进一步验证应该是通过rag召回数据，然后灌入到prompt中再让LLM推理选择的。

## 输出
输出的结果是书籍的名字，作者，简介，推荐理由，点击链接可以直接进入起点看书。

## 总结
这个场景其实和我们的场景相似一些，都是有了一定数量的产品，并且这些产品相对稳定（小说的更新速度在起点其实不高，因为起点对AI书籍的管控比较严格）。 

并且，这里我个人认为存在一些相似，比如小说，用户可能需要玄幻，大作家，连更，等标签。  
  
在基金或者股票中同样存在，大私募/公募，稳定，高收益，等等标签。

# vivo浏览器搜索
## 背景
针对搜索的query，阅读多个资料进行一次系统性的总结。但是这个总结和web端的AI搜区别不大

## 模型
这里不知道用的什么模型，但是返回速度挺快的，猜测没有使用cot，并且应该是flash版本

## 数据召回
直接返回的搜索引擎估计是搜索引擎返回的多个网页，然后把这些网页的内容做了总结。

## 总结
类似于百度的AI搜，本身其实更多的是对web的元信息总结，其实不涉及太多的召回和个性化优化。甚至我们可以认为本身就是在ds后面接了一个web search的接口，甚至对web的搜索结果都没有进行观察。
